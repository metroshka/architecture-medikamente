# Тегирование данных в «Медикаменте»

Для журнала записи и результата анализа нужны разные правила доступа. Администратор ресепшена вправе уточнить, к кому записан пациент. Открывать показатели исследования для этого ему незачем. Я предлагаю помечать документы по тому, какие сведения в них есть, и проверять эти метки при выдаче. Отдельно нужно проверять, с каким пациентом и в какой роли работает сотрудник.

## Что помечать

У одного документа может быть несколько меток. Например, в расчетной ведомости есть и сведения о сотруднике, и сумма выплаты. При выборе получателя должны выполняться ограничения по каждой метке. Ранее выбранные [способы защиты](03-data-protection.md) привязаны к тем же процессам P01–P08.

| Процесс и объект | Какие метки присвоить | Что учесть при выдаче |
| --- | --- | --- |
| P01. Реестр пациентов и договор | «Персональные данные». Для документа, подтверждающего обращение за медпомощью, добавить «Обращение» | Для сверки одного договора выдать сведения по этому договору. Весь реестр остается у ресепшена. |
| P02. Журнал записи к врачу | «Персональные данные», «Обращение» | Ресепшен ведет расписание, врач видит записи на свои приемы. |
| P03. Медкарта и расширенная анкета | Для медкарты — «Персональные данные», «Обращение», «Медицинские данные». Анкета с указанием хронических заболеваний тоже получает медицинскую метку | Лечащему врачу доступна карта его пациента. Для регистрации из анкеты нужны только административные поля. |
| P04. Реестр анализов и результат | «Персональные данные», «Обращение». Для результата исследования добавить «Медицинские данные». Дневной реестр получает эту же метку, если в нем есть клинические сведения | При выдаче результата проверить, к какому направлению он относится. Номер направления сохраняет связь с пациентом и после удаления ФИО. |
| P05. Платеж и чек | «Финансы». Если по записи можно установить, кто оплатил обращение за медпомощью, добавить «Персональные данные» и «Обращение» | Для сверки кассиру передавать номер операции, сумму и статус. |
| P06. Начисление зарплаты | «Кадры», «Персональные данные», «Финансы» | Доступ к платежам в 1С сам по себе не дает кассиру права читать ведомость. |
| P07. ТМЦ и закупки | «Внутренние данные». Для документа с именем и контактами представителя поставщика добавить «Персональные данные» | При обмене с бухгалтерией учитывать поля, которые фактически входят в выгрузку. |
| P08. Выборка аналитика и готовый отчет | Рабочая копия наследует метки источников. Для проверенной сводки P&L оставить «Финансы», для ABC по количеству единиц ТМЦ — «Внутренние данные» | Проверить итоговую книгу и сохраненный вывод ячеек Jupyter. В сводке по редкой услуге даже одна строка без ФИО иногда позволяет узнать пациента. |

## Кто ставит метку и где она хранится

**На общем диске.** Для Windows Server 2022 предлагаю File Server Resource Manager (FSRM). Если общий диск использует NTFS, администратор может создать свойство «Категории данных» с выбором нескольких значений. Для файлов в папке медкарт правило срабатывает по их расположению. Так скан JPG получит медицинскую метку, даже если в нем нельзя искать текст. Сначала нужно разметить накопленные файлы, затем проверять новые и измененные по расписанию. Пока категория неизвестна, файл доступен только в закрытой папке разбора. Права на исходники задают через группы Active Directory и разрешения на папки. [Классификация файлов в Windows Server][fsrm] · [Типы свойств FSRM][properties]

**В таблицах и 1С.** Владелец процесса и администратор фиксируют в реестре правил тип документа, названия полей, их категории и допустимых получателей. Медицинские поля определяет назначенный врач, платежные и зарплатные — ответственный бухгалтер. Метки книги Excel учитывают все листы, включая скрытые. Для отдельной выгрузки 1С правила задают по полям шаблона. Права внутри самой базы задают ролями 1С. В реестре правил достаточно названий полей и версии шаблона.

**При обмене.** Для регулярной передачи выгрузок предлагаю Apache NiFi. На файловом сервере скрипт читает категории через FSRM. Для выгрузки из 1С их определяет утвержденный шаблон. Вместе с файлом по защищенному каналу передаются идентификатор выгрузки, версия шаблона, категории и контрольная сумма файла. [Чтение свойств FSRM][read-property]

На входе нужно проверить отправителя, версию шаблона, состав полей структурированной выгрузки и обязательные метки. В NiFi процессор `UpdateAttribute` записывает проверенные категории в атрибуты потока. По правилам `RouteOnAttribute` файл отправляется только разрешенному получателю. Тот сверяет контрольную сумму перед загрузкой и сохраняет категории рядом с документом. Файл с неизвестным полем, потерянной меткой или неверной суммой остается в закрытой очереди. В журнал передачи попадают номер выгрузки, источник, получатель, версия правил и решение. По этим данным можно проследить путь файла, не копируя в журнал его содержимое. Для ручной пересылки через Outlook и записи на носители ограничения нужны на почте и рабочих местах. [UpdateAttribute][update] · [RouteOnAttribute][route]

## Как это сработает на результате анализа

1. При приеме результата клиника проверяет отправителя, тип документа и номер направления. По правилам P04 результат получает три метки из таблицы. Состав полей и канал предстоит согласовать с лабораторией.
2. Перед выдачей проверяются две связи. Направление должно относиться к этому пациенту, а врач должен участвовать в его лечении. Пока результаты лежат на общем диске, администратор выдает и отзывает права на папку пациента по подтвержденным назначениям. В журнал доступа попадают технический идентификатор документа, сотрудник, время и решение. Значения анализов остаются в медицинской карте.
3. При повторной выгрузке в PDF сохраняются те же ограничения. Если аналитику нужно число исследований за месяц, для него готовят отдельную сводку. Врач, ответственный за медицинские данные, проверяет состав полей и то, можно ли узнать пациента по редкой услуге или по разнице с другим отчетом. После проверки он может утвердить для этой сводки метку «Внутренние данные». До согласования действуют исходные ограничения. В журнале остаются прежние и новые метки, автор решения и его основание. У самого результата анализа метки сохраняются.

Для проверки я возьму два учебных направления, назначенных разным врачам. Каждый врач должен открыть результат своего пациента и получить отказ при попытке открыть второй. Еще два случая — запрос исходного результата аналитиком и передача файла с потерянной меткой. В первом случае ожидаю отказ в выдаче. Во втором файл должен остаться в закрытой очереди, а ответственный — получить уведомление. Эти примеры подходят и для повторной проверки после изменения правил или шаблона выгрузки.
